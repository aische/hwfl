# 2026-08

## 2026-08-07 — H-2: a crash is a run outcome, not a process exit

The run loop had no exception barrier, so a provider throw, a full disk during
persist, or a pure exception from H-3/H-4 killed the process while
`snapshot.json` still held the pre-step machine — a resume would then replay a
transition whose side effects had already happened (double `exec.run`, double
LLM spend). Contained at three boundaries, all on `Hwfl.Exception.trySync`:
`runHostOp` (→ `HostErr`, catchable), `safeLlmChat` (→ `ProviderError`, used by
all four model call sites), and `guardedStep` around every `stepMachine` call
in `runUntilPause` (→ `InternalErr`). The step barrier closes the spans the
crashed step opened and persists `MsFailed` before returning, so the durable
state matches what actually ran. `app/Main.hs` grew a last-resort handler so
anything escaping outside a run is still a `--json` error envelope.

### Decisions

- **Contained means synchronous only.** `trySync` re-throws
  `SomeAsyncException`, `ExitCode`, `ThreadKilled`, `UserInterrupt` and
  `HeapOverflow`: those are a request for this thread to stop, and swallowing
  them would break Ctrl-C, `exitWith`, and any future cancellation from the
  control plane. `StackOverflow` is deliberately treated as a run failure —
  deep author recursion is a program error and GHC has already unwound.
- **A crash is not catchable by author code.** `InternalErr` is a new
  `RuntimeError` constructor with `isCatchable = False`. A host op that throws
  is still `HostErr` (the op boundary is well-defined, so `try`/`catch` works
  as before), but an exception that escapes a *step* aborted at an unknown
  point, possibly after applying part of its effect; letting a workflow
  continue from there would be worse than failing.
- **Nested branch machines are not barriered separately.** Agent tool calls,
  `par` branches and `FrInvoke` nests call `stepMachine` directly, so their
  crashes reach the enclosing `runUntilPause` and fail the whole run rather
  than being recovered as "that tool call failed, keep going".
- Cleanup on the crash path (span close, persist) runs under its own
  `trySync`, so a store that also fails cannot replace the original error.

## 2026-08-07 — H-7: run ids are store keys, not path fragments

Run ids reached `workspace/.hwfl/runs/<id>` verbatim, so a library caller (or
`hwfl resume . ../../pwned`) could create directories and read/write
`meta.json` / `snapshot.json` anywhere the process can write. `validateRunId`
now accepts only a single portable path component (`A-Za-z0-9._-`, no leading
`.`, ≤ 128 chars), and the sole id→path mapping (`runDirFor`) validates first,
so a new backend cannot reintroduce the hole by joining an id itself.

The entry points collapsed to two: `createRun` for a start, `openRun` for a
continue. `openRunStore` / `tryOpenRunStore` are gone — they created the run
directory on the way in, which is why an unopenable run (unknown id, stale
project hash) still left a directory behind. Failure paths now take a pure
handle (`runStoreHandle`, creates nothing) or a detached one (no directory at
all: writes dropped, reads empty), so reporting an outcome for a run that was
never opened has no filesystem effect.

### Decisions

- **Starting a run is create-only.** `createRun` uses `createDirectory`, not
  `createDirectoryIfMissing`, so an id already in use is rejected without a
  check/create race. The report suggested an "unless explicitly intended"
  opt-in for reuse; there is no correct reuse semantics — the old snapshot and
  spans survive while meta is replaced and the sequence restarts, which is the
  exact corruption being fixed — so continuing an existing run stays the job of
  resume / step / approve, and no opt-in flag was added.
- Untrusted-input treatment applies to run ids, not just filesystem paths:
  they arrive from the control-plane API and from workflow code via
  `meta.read_spans` / `meta.read_snapshot`.
- A `RunStore` handle may be detached (`storeRoot :: Maybe FilePath`).
  Backend writes are no-ops on it rather than errors, so error paths can carry
  a store without a directory.

## 2026-08-07 — H-1 retracted; real escape was create-before-check (H-1a)

H-1 claimed `fs.write` / `fs.copy` followed dangling symlinks out of the
workspace. Attempting to write a proof-of-concept disproved it:

- `directory`'s `canonicalizePath` is not `realpath`. `realpathFurther`
  dereferences unresolved segments via `getSymbolicLinkTarget`, so a dangling
  link canonicalizes to its resolved-but-missing target. The old leaf check
  therefore saw an out-of-root path and returned `SandboxErr`.
- `copyFile` is temp-file + `copyPermissions` + `rename`, and `rename` never
  follows a symlink on the final component, so the copy replaced the link
  in place. Never an escape.

Replaying the HEAD~1 logic against dangling and live out-of-workspace links
blocked all four cases. The report entry is retracted with the measurements.

**The genuine bug found while disproving it (H-1a):** every mutating op ran
`createDirectoryIfMissing` and *then* checked containment, so
`fs.mkdir("dirlink/escaped")` through an in-workspace directory symlink
created the directory outside the root before failing. Fixed by
`ensureDirUnderRoot`, which descends one component at a time from the
canonical root and checks before each `createDirectory` — the cursor is
canonical and contained at every step, so nothing outside can be created.

Also fixed, none of it in the original report:

- `fs.remove` on a *directory* symlink canonicalized and then
  `removeDirectoryRecursive`'d the **target**. Silent data loss outside the
  sandbox; now the link is unlinked. The worst bug in this area.
- `fs.copy` had lost atomicity and permission preservation when it stopped
  using `copyFile`; restored via `O_EXCL` temp + `rename`, and a
  file-onto-file overwrite is no longer pre-removed, so the destination
  survives a failed copy.
- `fs.exists` and `fs.stat` disagreed on dangling links (`true` vs a hard
  error). A symlink is now consistently an existing entry with
  `kind = "symlink"`.
- Leaf symlinks are followed when they resolve inside the workspace, so
  writes are symmetric with reads and internal aliases keep working.
- `ELOOP` detection moved from matching the locale-dependent `strerror`
  string to `ioe_errno`.

### Decisions

- Mutating ops never trust a path that was validated before use: containment
  is checked before each component is created, and the final open is
  `O_NOFOLLOW` (or a `rename`, which cannot follow). Check-then-use is only
  acceptable when the use itself is symlink-proof.
- Sandbox policy is symmetric: a symlink is followed iff it resolves inside
  the workspace, for reads and writes alike.
- A symlink is a directory entry, not its target: it exists, it stats as
  `"symlink"`, and removing it does not touch what it points at.
- `[Verified]` in the bug report means "code read", not "failure reproduced".
  Security findings need an executed PoC before they are acted on; H-1 cost a
  round of regressions because a library contract was assumed rather than run.
- `Workspace` is POSIX-only (`unix`: `O_NOFOLLOW`, `lstat`, `fchmod`). No
  Windows support is planned; revisit with CPP if that changes.

## 2026-08-07 — H-6: function-call shapes preserve checker/runtime agreement

An empty call now rejects every non-`Unit` function domain instead of returning
the function type. Runtime binding supplies `VUnit` for an omitted `Unit`
parameter, so successful `f()` calls have the same interpretation at both
layers. A one-parameter record function now packs individually supplied
positional or named fields into that record; multi-parameter functions retain
their existing positional/named binding. `fs.write` also accepts its
two-position argument form, which the checker has always validated.

### Decision

- A record domain represents both the type of multi-parameter functions and a
  single record parameter. Its runtime `Param` metadata resolves the ambiguity:
  one annotated record parameter receives a constructed record, while multiple
  parameters bind individually. This preserves the concise multi-argument
  language surface without an invasive callable-shape annotation in `TypeExpr`.

### Follow-up

Post-fix review kept H-6 closed and filed **M-19** for the leftovers: host
ops that still parse only named fields while the checker unpacks record
domains; whole-record calls to multi-parameter functions (same `TypeExpr`
ambiguity in the other direction); and Unit/record packing that keys off
syntactic annotations rather than resolved types.

## 2026-08-07 — H-3: JSON numbers retain their mathematical value

`jsonToValue` previously narrowed every JSON `Scientific` number to `Double`
before deciding whether it was an integer. It now uses `floatingOrInteger`:
integral values go straight to arbitrary-precision `VInt`; non-integral values
use the runtime's `Double` `VFloat` representation and reject a non-finite
conversion. The error flows through `llm.object`, agent submit/tool arguments,
and meta-read values as a normal failure. Regression coverage includes the
first non-representable integer above 2^53 and nested values.

## 2026-08-07 — H-4: non-finite Float is a language error

Float literals and arithmetic now construct values through `finiteFloat`, which
rejects NaN and Infinity as `Trap`s. Overflow therefore stops before the
machine can persist an invalid value. JSON encoding is now recursively fallible
and string interpolation likewise rejects non-finite values, protecting those
boundaries against a malformed value introduced by future internal code. Agent
tool-result serialization converts that boundary failure into its existing
recoverable tool-error path.

### Decision

- **Finite `Double` is a runtime invariant.** IEEE special values are neither
  JSON values nor valid snapshot payloads, so they must not be represented by
  `VFloat`. Serialization checks remain as a defense-in-depth boundary, not a
  lossy conversion to JSON strings or `null`.

## 2026-08-07 — H-5 / L-19: bounded agent round budgets

`nextPow2` previously enumerated powers of two in `Int`; after the sign bit,
the sequence wrapped negative and the exhausted-agent hint loop never
terminated. It now doubles with a pre-overflow guard and saturates. Suggested
extensions are also capped to the remaining `Int` headroom, yielding zero when
no further representable extension exists.

Source `max_rounds` rejects positive integers that cannot fit `Int`; persisted
agent state rejects non-positive budgets and counters. Extending a paused agent
now rejects non-positive increments and checks addition before changing the
machine, so neither source nor resume paths can wrap the budget.
